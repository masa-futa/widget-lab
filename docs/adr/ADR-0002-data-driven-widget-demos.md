# ADR-0002: Widget のデモをプロパティの定義のデータから組み立てる

> **要約**
> - 結論: Widget 1つを `WidgetEntry`（プロパティの定義の一覧＋組み立ての関数）で表し、操作パネル・プレビュー・比較・コードを全部そこから作る
> - 影響: 収録するすべての Widget（`lib/catalog/`）と、詳細画面のすべて
> - お願い: なし（2026-10-28 オーナー承認）

## ステータス
承認済み（2026-10-28）

## 背景
PRD は、公式 Widget カタログの全ジャンル・全 Widget（数百件）を収録してからリリースすると決めている。1つ足す手間が大きいと、全部を収録しきれない（構想ブリーフの「最大の未検証リスク」）。PRD の「デモの組み立て」は、プロパティの定義のデータから組み立てることを求めている。

## 決定
- 収録データの型は docs/design/functions/demo-engine.md の「収録データの型」のとおり（`WidgetEntry`・`PropertySpec`・`PropertyControl` とその種類・`DemoBuilder`）
- `PropertyControl` が「操作部品」「Dart の値への写し方（`resolve`）」「コードの書き方（`code`）」を1つに持つ。操作部品が扱う値は少数の種類（スライダー・スイッチ・選択・色・文字・固定）に絞る
- 1 Widget = 1 ファイル（`lib/catalog/<ジャンル>/<widget>.dart`）。組み立ての関数だけは Widget ごとに手で書き、OFF のプロパティには Widget の既定値を渡す
- 見た目を持たない Widget も同じ型に載せ、`kind: behavior` と `DemoProbe` で可視化する
- 全件の組み立て（全部 OFF・全部 ON・各選択肢）と、公式カタログの一覧（`manifest.dart`）との突き合わせをテストで行う

## 選ばなかった案
| 案 | 選ばなかった理由 |
|---|---|
| Widget ごとに手書きのデモ画面（操作パネルとコードも Widget ごとに書く） | 数百件で手間と見た目のばらつきが大きく、全部を収録しきれない。比較とコードの仕組みも Widget ごとに書くことになる |
| Flutter の SDK を analyzer で読み、プロパティの定義を自動で作る | 型ごとの操作部品・代表の値・日本語の説明は結局手で決める必要がある。ビルドの仕組みが重く、Flutter の版ごとに壊れやすい |
| 組み立ての関数もなくし、リフレクションでコンストラクタを呼ぶ | Flutter では `dart:mirrors` を使えない |

## 結果
- Widget を1つ足すのは、1ファイルにプロパティの定義と組み立ての関数を書くだけになる。操作パネル・比較・コード・テストは共通で動く
- 引き受けること: 組み立ての関数で、OFF のときの既定値を手で合わせる必要がある（Dart では引数を条件つきで省けないため）。Flutter の版が上がって既定値やプロパティが変わったら、収録データを直す
- 見直すきっかけ: 型に載らない Widget が多く出てきたとき（例: 複数の子の並べ替えが要る Widget）、Flutter の SDK にプロパティの情報を取り出す公式の手段ができたとき
